# P3 — Spec penuh

**Status:** P3a + P3b + P3c implemented  
**Depends on:** P1 checks · P2 services / check history / floor rack-zone / skip-poller-when-agent  
**Out of scope:** P4 APM / deep DB (integrasi vendor, bukan build in-house)

---

## 1. Tujuan produk

P3 menaikkan NETMON dari “up/down + synthetic jitter” ke **infra monitoring yang dapat diatur**:

1. **Alert rules** — event & severity dari threshold / kondisi, bukan hanya hard-coded `device_down`.
2. **Maintenance windows** — suppress alert, notify, dan auto-ticket saat jadwal maintenance.
3. **SNMP poll** — metric nyata dari network gear (ganti jitter untuk device yang dikonfigurasi SNMP).
4. **Facility sensors** — suhu / humidity / power sebagai inventory + probe.
5. **Floor heat map** — overlay suhu/util pada denah (di atas pin zone/rack P2).

Portal tetap **kaca** (read-only). NOC tetap **kemudi**.

---

## 2. Non-goals (eksplisit)

| Bukan P3 | Alasan |
| --- | --- |
| Full APM / distributed tracing / DB query analysis | P4 — integrasi |
| Network discovery / auto-topology dari SNMP walk penuh | Terlalu lebar; P3 = poll OID curated |
| Live CCTV / VMS | Sudah ditolak di MONITORING |
| SNMP **trap ingest** sebagai event bus | Opsional later; P3 fokus fokus **SNMP GET**. Channel type `snmp` (trap **outbound**) boleh dilengkapi terpisah |
| Multi-poller geo / remote probe farm | Arsitektur terpisah |
| Mengubah model multi-tenant / RBAC roles | Pakai permission yang ada |

---

## 3. Prinsip desain

1. **Satu codebase** cloud + on-prem (`IS_SAAS` tidak mengubah fitur P3).
2. **Tenant isolation** — semua query `tenant_id`.
3. **Poller tetap sumber kebenaran status**; rules **mengevaluasi** hasil poll / metric, tidak menjalankan perintah ke device.
4. **Maintenance = silence**, bukan mengubah status device menjadi `up`.
5. **Backward compatible** — tanpa rule baru, perilaku P2 tetap: down → `device_down` critical → notify + auto-ticket.
6. **UI** Datadog/Linear: tenang, mono untuk OID/IP/hostname, tidak rainbow.

## 5. P3a — Alert rules & maintenance windows

### 5.1 Masalah hari ini

- Poller hanya emit `device_down` (`lib/poller.ts`).
- Tidak ada silence → maintenance selalu memicu channel + ticket.
- Connector ticketing sudah punya filter `events` / `severities`, tapi event selain `device_down` belum ada.

### 5.2 Model data

```prisma
model alert_rule {
  id          String   @id @default(cuid())
  tenant_id   String
  name        String
  enabled     Boolean  @default(true)
  /// device_down | check_degraded | high_latency | metric_cpu | metric_ram | metric_disk | snmp_threshold | sensor_threshold
  event       String
  /// critical | warning | info
  severity    String   @default("warning")
  /// null = semua device tenant; else filter
  device_id   String?
  /// type filter opsional: switch, server, application, …
  device_type String?
  /// JSON threshold / params (lihat §5.3)
  config      Json     @default("{}")
  /// detik kondisi harus bertahan sebelum fire (anti-flap)
  for_seconds Int      @default(0)
  created_at  DateTime @default(now())
  updated_at  DateTime @updatedAt

  tenant tenant @relation(...)
  device device? @relation(...)
  @@index([tenant_id, enabled])
  @@index([tenant_id, event])
}

model maintenance_window {
  id          String   @id @default(cuid())
  tenant_id   String
  name        String
  /// all | devices | types
  scope       String   @default("all")
  /// JSON: { "device_ids": [] } | { "types": ["switch"] }
  scope_config Json    @default("{}")
  starts_at   DateTime
  ends_at     DateTime
  /// suppress_notify | suppress_ticket | suppress_alert (default: ketiganya true via flags)
  suppress_alert  Boolean @default(true)
  suppress_notify Boolean @default(true)
  suppress_ticket Boolean @default(true)
  note        String?
  created_by  String?
  created_at  DateTime @default(now())

  tenant tenant @relation(...)
  @@index([tenant_id, starts_at, ends_at])
}
```

**Alert row (tambahan opsional P3a):**

| Field | Perubahan |
| --- | --- |
| `alert.rule_id` | nullable FK → `alert_rule` (null = legacy hard-coded) |
| `alert.message` | nullable text singkat untuk UI (“latency 850ms > 500ms”) |

Index lama `(device_id, event, status)` tetap dipakai untuk dedupe firing.

### 5.3 `alert_rule.config` (kontrak)

| `event` | `config` contoh | Fire ketika |
| --- | --- | --- |
| `device_down` | `{}` | status device = `down` (sama P2; rule default seed) |
| `check_degraded` | `{}` | status = `degraded` |
| `high_latency` | `{ "ms": 500 }` | `last_check_latency_ms` ≥ ms |
| `metric_cpu` / `metric_ram` / `metric_disk` | `{ "percent": 90 }` | sample metric terbaru ≥ percent |
| `snmp_threshold` | `{ "oid_key": "if_errors", "op": ">", "value": 100 }` | P3b |
| `sensor_threshold` | `{ "metric": "temp_c", "op": ">", "value": 28 }` | P3c |

`for_seconds > 0`: evaluasi menyimpan state di Redis key `rule:{tenant}:{rule}:{device}` (atau tabel kecil `alert_rule_state`) sampai kondisi bertahan.

### 5.4 Default rules (seed per tenant baru + migrate backfill)

Untuk setiap tenant aktif, buat **satu** rule enabled:

- name: `Device down`
- event: `device_down`
- severity: `critical`
- `for_seconds`: 0

Sehingga perilaku produksi tidak berubah setelah deploy P3a.

### 5.5 Evaluasi (poller)

Setelah `pollDevice` + `persistCheckSample` (+ metric):

```text
1. Tentukan kandidat event dari hasil poll (down / degraded / latency / metric).
2. Load alert_rule enabled untuk tenant (cache 30–60s OK).
3. Match device_id / device_type.
4. Jika dalam maintenance_window aktif yang cover device:
     - suppress_alert  → jangan create alert
     - else create alert dengan tag/message “IN MAINTENANCE” hanya jika suppress_alert=false
     - suppress_notify → skip notifyAlert
     - suppress_ticket → skip maybeOpenTicketsForAlert
5. Else: create/resolve seperti sekarang, severity dari rule (bukan hard-code critical).
6. Resolve: bila kondisi hilang, resolve semua firing untuk (device, event) yang cocok.
```

**Legacy path:** jika tenant belum punya rule `device_down`, fallback ke perilaku P2 (defensive). Setelah backfill, path ini dead.

### 5.8 Acceptance P3a

- [ ] Tenant baru punya default `Device down` rule.
- [ ] Tanpa rule ekstra, down → critical alert + notify + ticket (sama P2).
- [ ] Window aktif + `suppress_*` true → **tidak** ada alert/notify/ticket baru untuk device in-scope.
- [ ] Setelah window berakhir, down berikutnya fire normal.
- [ ] Rule `high_latency` dengan threshold rendah menghasilkan alert `warning` (atau severity yang di-set).
- [ ] Viewer 403 pada POST rules/maintenance.
- [ ] Operator bisa CRUD rules/windows; tidak perlu `channels.manage`.

## 6. P3b — SNMP GET

### 6.1 Masalah hari ini

- `metric` diisi **jitter** di poller bila agent tidak fresh (`docs/MONITORING.md`).
- Tidak ada community / OID di `device`.
- Channel catalog `snmp` = trap outbound stub, **bukan** poll.

### 6.2 Model data

```prisma
/// Profil OID reusable per tenant (atau system templates)
model snmp_profile {
  id         String @id @default(cuid())
  tenant_id  String?  /// null = system template (read-only di UI)
  name       String   /// "IF-MIB basics", "Cisco CPU", …
  /// JSON array: [{ "key": "cpu", "oid": "…", "metric": "cpu_percent" | "custom", "scale": 1 }]
  oids       Json
  created_at DateTime @default(now())
}

/// Kredensial + binding di device (kolom device atau tabel 1:1)
/// Prefer kolom di device untuk query poller sederhana:
device.snmp_enabled     Boolean @default(false)
device.snmp_version     String?  /// v2c | v3
device.snmp_community   String?  /// encrypt at rest dengan ENCRYPT_KEY (sama pola secret lain)
device.snmp_port        Int     @default(161)
device.snmp_profile_id  String?
/// v3 fields opsional: snmp_v3_user, snmp_v3_auth_proto, snmp_v3_auth_key, snmp_v3_priv_…
```

Simpan community **terenkripsi** (AES via `ENCRYPT_KEY`); jangan log plaintext.

### 6.3 Poller

Urutan metric write di `pollDevice` (setelah reachability checks):

```text
1. Jika agent metric < 90s → pakai agent (existing).
2. Else jika snmp_enabled + profile → SNMP GET curated OIDs → map ke cpu/ram/disk dan/atau metric_extra.
3. Else → jitter (existing) HANYA jika device.type bukan sensor; dokumentasikan sebagai "placeholder".
```

Library: paket SNMP Node yang sudah mature (mis. `net-snmp` / setara); timeout ketat (2–3s); max OID per device (mis. 32).

**Reachability:** SNMP gagal total **tidak** otomatis = `device_down` kecuali rule/check mengatakannya. Status up/down tetap dari P1/P2 checks (TCP/HTTP/ICMP) kecuali device type khusus `sensor` (P3c).

### 6.4 Metric extension

Opsi A (disarankan P3b minimal): tetap `metric.cpu_percent|ram_percent|disk_percent`; OID lain masuk `device.last_check_detail` / JSON `metric_extra` baru.

Opsi B: tabel `metric_sample (device_id, key, value, ts)` — lebih fleksibel, lebih kerja. **Spec default = Opsi A + `metric_extra Json?` pada `metric`.**

### 6.5 API / UI

| Method | Path | Permission |
| --- | --- | --- |
| GET/POST | `/api/snmp/profiles` | `assets.read` / `assets.write` |
| PATCH/DELETE | `/api/snmp/profiles/{id}` | `assets.write` |
| PATCH device | existing | fields SNMP (community write-only: GET mengembalikan masked) |

UI: Inventory → panel **SNMP** (enable, version, community, profile). Services page **tidak** perlu SNMP.

Portal: tampilkan “SNMP enabled” boolean saja; **jangan** community.

### 6.6 System profiles (seed)

Minimal:

1. **Host resources-ish** — map ke cpu/ram jika OID standar tersedia; jika tidak, profile “Interface counters only”.
2. **IF-MIB** — `ifInOctets` / `ifOutOctets` / `ifOperStatus` → `metric_extra`.

Exact OID list difinalisasi saat implementasi (uji terhadap switch lab). Spec mengunci **kontrak JSON**, bukan daftar OID final.

### 6.7 Acceptance P3b

- [ ] Device SNMP enabled + community benar → metric non-jitter (nilai stabil antar poll bila load stabil).
- [ ] Community salah → log/detail error; status device tidak flip random; tidak leak community di API/UI logs.
- [ ] Device tanpa SNMP tetap jitter atau agent (P2).
- [ ] Rule `metric_cpu` memakai nilai SNMP.
- [ ] On-prem tanpa internet: SNMP lokal jalan (tidak depend cloud LLM).

## 7. P3c — Facility sensors & floor heat map

### 7.1 Sensor sebagai device

| Aspek | Keputusan |
| --- | --- |
| Inventory `type` | `sensor` (tambah ke katalog type) |
| Subtype | `checks` atau field `sensor_kind`: `temperature` \| `humidity` \| `power` \| `other` |
| Probe | HTTP JSON (`$.temp_c`), SNMP OID (butuh P3b), atau agent push ke heartbeat extension |
| Status | Threshold rule (`sensor_threshold`) → degraded/down opsional; default: selalu `up` jika probe berhasil baca angka |

Simpan reading terakhir:

```text
device.last_sensor_value   Float?
device.last_sensor_unit    String?  /// C | % | W
device.last_check_latency_ms  (existing)
```

History: boleh reuse `device_check_result.detail` atau `metric_extra`.

### 7.2 Floor heat map

**Data:** placement + device type `sensor` (atau server dengan SNMP temp) dalam radius/zone yang sama.

**UI:** `/dashboard/floors` toggle **Heat** (operator). Canvas overlay:

- Grid interpolasi sederhana (IDW) dari pin sensor → warna dingin→hangat (satu ramp, bukan rainbow badge spam).
- Legend mono: `18°C — 32°C`.
- Tanpa sensor di floor → empty state (“Add temperature sensors to this floor”).

**Portal:** heat read-only jika tenant punya sensor; sama data.

**Bukan:** CFD, 3D rack elevation, live camera.

Schema: **tidak wajib kolom baru** jika heat dihitung on-read dari placements + `last_sensor_value`. Opsional cache `floor.heat_cache Json` bila berat.

### 7.3 Acceptance P3c

- [ ] Device type `sensor` + HTTP JSON probe menampilkan nilai + unit di Inventory.
- [ ] Rule `sensor_threshold` fire saat di atas batas.
- [ ] Floor dengan ≥2 sensor temp menampilkan overlay heat yang bergerak saat nilai berubah.
- [ ] Portal floors heat visible, tidak editable.

## 10. Worker / performa

| Constraint | Target |
| --- | --- |
| Poll interval | tetap ~60s (BullMQ existing) |
| SNMP timeout | ≤3s per device |
| Rules eval | O(rules × devices_polled) per tick; cache rules |
| Heat | hitung di request UI atau cache 60s; jangan di critical path poller |
| History retention | `device_check_result` keep policy P2; metric tetap prune jika sudah ada job |

Cloud SaaS: SNMP ke private IP **tetap gagal** dari VPS publik — sama batasan MONITORING §2; dokumentasikan: SNMP untuk on-prem atau device public SNMP (jarang). Agent/sensor HTTP yang reachable tetap valid di cloud.
